# 설계와 보안

## 공개/비공개 경계

```text
개인 작업 공간                 공개 저장소 / 정적 호스팅
PDF·출처 → 구조화 원문 ─┐
해설·법령/판례 근거 ────┤ 검증 → 암호화된 단원 묶음
별도 보관한 256비트 키 ─┘             ↓
                           링크의 #key로 브라우저 복호화
                                      ↓
                           암호화된 브라우저 학습 기록
```

공개 저장소에는 화면 코드, 스키마, 도구, 암호문만 둡니다. 원문·해설·출처의 실제 목록과 개인키는 저장소 밖 별도 디렉터리에 둡니다. 암호화는 로컬에서 끝나며 배포 과정은 키를 알 필요가 없습니다. 해시·배포 시각·암호문 크기는 공개 정보입니다.

## 암호화

- 브라우저/Node Web Crypto의 AES-256-GCM. 암호화마다 무작위 96비트 IV를 생성합니다.
- 무작위 256비트 마스터키에서 HKDF-SHA-256으로 용도별 키를 파생합니다.
- 콘텐츠 배포판·단원, 학습 기록, 백업의 용도를 분리하고 AAD에 결합합니다.
- URL 쿼리가 아닌 fragment `#key=...`로 키를 전달합니다. [fragment는 HTTP 요청으로 서버에 전송되지 않습니다](https://developer.mozilla.org/en-US/docs/Web/URI/Reference/Fragment).
- 해시는 파일 손상을 확인하는 용도이며, 인증은 AES-GCM 태그가 담당합니다. [AES-GCM의 IV 요건](https://developer.mozilla.org/en-US/docs/Web/API/AesGcmParams)을 따릅니다.

**이 구조는 로그인 기반 접근 통제가 아닙니다.** 링크가 유출되면 자료를 읽을 수 있습니다. 키는 주소창·방문 기록·북마크에 남을 수 있습니다. 확장 프로그램, 악성 스크립트, 공유 PC에서 열린 세션까지 보호하지 못합니다. 저장소나 호스팅이 공격받아 악성 앱이 배포되면 이후 입력되는 키도 탈취될 수 있습니다. 코드 변경을 검토하고 계정 보안을 유지해야 합니다.

키를 바꿔도 이미 내려받은 이전 암호문과 이전 키를 회수할 수는 없습니다. 키를 분실하면 복구할 서버가 없습니다. 원본과 키를 별도로 백업해야 합니다.

## 화면과 기록

복호화된 문제는 메모리에만 유지합니다. 기록은 별도 도메인 키로 암호화해 localStorage에 저장합니다. 평문 키 자체를 localStorage에 저장하지 않습니다. 저장 작업을 직렬화해 늦은 쓰기가 최신 기록을 덮지 않게 합니다.

문항 ID를 기준으로 익숙한 정도·읽음·형광펜을 연결합니다. 본문 수정은 내용 버전, 정답 수정은 평가 버전을 올립니다. 평가 버전이 다르면 읽음을 취소하고 다시 확인하도록 표시합니다. 형광펜은 인용문과 앞뒤 문맥으로 복구하며 확실하지 않으면 원래 표시를 별도로 보여 줍니다.

회독 시작 시 문항 ID 집합을 고정합니다. 필터나 자료 추가로 분모가 바뀌지 않습니다. 삭제된 문항의 기존 기록도 유지합니다. 새로운 범위는 다음 회독에서 반영됩니다.

기록의 버전 1을 검증하며 알 수 없는 버전은 조용히 변환하지 않고 거부합니다. 손상 기록을 임의로 덮어쓰지 않고 복원 화면을 제공합니다. 여러 탭의 동시 편집·기기 간 자동 동기화는 지원하지 않습니다. 한 기기에서 한 탭으로 사용하고 이동 전 백업하세요.

## 배포

Vite + React + TypeScript의 정적 출력물을 GitHub Pages로 배포합니다. [GitHub 공식 사용자 지정 워크플로](https://docs.github.com/en/pages/getting-started-with-github-pages/using-custom-workflows-with-github-pages)를 사용합니다. 원격 분석·외부 폰트·외부 실행 스크립트는 사용하지 않습니다. CSP, no-referrer, 외부 링크 noopener/noreferrer를 적용합니다.
